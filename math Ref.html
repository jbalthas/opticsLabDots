PIV Ground Truth Generator
Flow Mathematics Reference

How particles move, why they move that way, and how to verify the math is correct
Prepared by: Jack (Lab Engineer) Date: June 2026 Version: 1.0

0 What This Document Is For

The PIV Ground Truth Generator is a browser-based tool that displays a synthetic field of moving particles. Its purpose is to act as a calibration reference: because we control exactly how fast every particle moves, a researcher can measure the apparent velocity from the video and compare it to the known correct answer.

This document explains, in plain English and then in precise mathematics, every rule the tool uses to decide where each particle goes each frame. A technically inclined reader can use the formulas to independently verify that the code is doing what it claims.

1 From Real-World Speed to Pixels on Screen

Plain English: The tool works in real units (meters per second). Before anything moves, it converts that real speed into "how many pixels per second should each particle travel," using the known physical size of the display screen and its resolution.

Scale Calibration

The user enters the physical dimensions of the TV screen (in millimetres) and the display resolution (in pixels). From these, the tool calculates a scale factor:

Eq. 1 px_per_mm_X = resolution_width_px / TV_width_mm px_per_mm_Y = resolution_height_px / TV_height_mm px_per_mm = ( px_per_mm_X + px_per_mm_Y ) / 2 ← average scale

With default values (1920 × 1080 px on a 1543.05 × 863.6 mm screen):

px_per_mm_X = 1920 / 1543.05 ≈ 1.2443 px/mm px_per_mm_Y = 1080 / 863.6 ≈ 1.2503 px/mm px_per_mm ≈ 1.2473 px/mm

Converting m/s to px/s

The user-facing speed control is in metres per second. Internally, the tool works in pixels per second using:

Eq. 2 speed_px_per_s = speed_m_per_s × 1000 × px_per_mm

The factor of 1000 converts metres to millimetres (1 m = 1000 mm), and then px_per_mm converts millimetres into pixels.

Verification example
Vx = 0.08 m/s, px_per_mm = 1.2473 px/mm
speed_px_per_s = 0.08 × 1000 × 1.2473 = 99.8 px/s ✓

2 Basic Particle Motion (No Obstacle)

Plain English: Without any obstacle present, every particle moves in a straight line at a constant speed. Each frame, the particle's position is updated by multiplying its velocity by the time that has passed since the last frame. If a particle drifts off the edge of the screen, it reappears on the opposite side.

Position Update

Eq. 3 x_new = x_old + Vx_total × Δt y_new = y_old + Vy_total × Δt

where Δt is the elapsed time in seconds since the last animation frame (typically about 1/60 s at 60 Hz display). The total velocity Vx_total includes turbulence, described in Section 4.

Wraparound (Periodic Boundary)

When a particle exits one edge it enters from the opposite edge, so the screen acts as a seamless, infinite flow field:

Eq. 4 x = ( x_new mod W + W ) mod W y = ( y_new mod H + H ) mod H

The double mod operation ensures the result is always positive regardless of direction of travel.

3 Flow Around an Obstacle

Plain English: When a circular obstacle is placed on the screen, particles must travel around it. The tool uses a well-established physics formula — called potential flow around a cylinder — to calculate exactly how the flow bends near the obstacle. This is not a simulation or approximation; it is the exact mathematical answer for an ideal (smooth, frictionless) fluid flowing around a perfectly round object.

Background: What Is Potential Flow?

Potential flow is a classical result from fluid mechanics. It describes how an ideal fluid (one with no viscosity — no internal friction) flows past a smooth obstacle. The fluid must go around the object — it cannot pass through it — and the solution satisfies two physical laws:

  • Conservation of mass (the fluid doesn't pile up anywhere)
  • Irrotationality (no spinning eddies or swirls in the flow)

For a circular cylinder, mathematicians solved this problem exactly over a century ago using a branch of mathematics called complex analysis. The result is a clean, closed-form formula.

Derivation

The derivation starts with the complex potential for a uniform upstream flow (U, V) past a cylinder of radius R at the origin:

Eq. 5 w(z) = (U − iV) z + (U + iV) R² / z

Here z = x + iy is a complex number representing the 2-D position. The first term is the undisturbed background flow; the second term (called a doublet) represents the disturbance caused by the cylinder.

Taking the derivative gives the complex velocity dw/dz = u − iv:

Eq. 6 dw/dz = (U − iV) − (U + iV) R² / z²

Substituting z² = (x²−y²) + 2ixy and separating real and imaginary parts yields the final velocity field:

Eq. 7 u = U − R² [ U(x²−y²) + 2Vxy ] / r⁴ v = V + R² [ V(x²−y²) − 2Uxy ] / r⁴

where r² = x² + y² is the squared distance from the obstacle centre, and x, y are measured relative to the obstacle centre.

What the Code Computes

In the tool, these formulas appear as:

Code (exact) dx2dy2 = dx² − dy² ← same as (x²−y²) dxy2 = 2 · dx · dy ← same as 2xy vx = U − R² · (U·dx2dy2 + V·dxy2) / r⁴ vy = V + R² · (V·dx2dy2 − U·dxy2) / r⁴

This is identical to Equation 7. The code is a direct, term-for-term implementation of the analytic formula.

Boundary Condition Proof

A critical requirement is that no fluid passes through the cylinder wall. At the surface (r = R), the velocity component pointing directly toward or away from the centre (the radial component) must equal zero.

Converting to polar coordinates at r = R (using x = R cosθ, y = R sinθ):

Eq. 8 v_radial = u cosθ + v sinθ = 2U cosθ sin²θ − 2V sinθ cos²θ + 2V sinθ cos²θ − 2U sin²θ cosθ = 0 ✓

All four terms cancel. The cylinder wall is, as required, a perfect streamline.

Verification: stagnation point
For pure x-flow (V = 0), the leading stagnation point is directly upstream at (x = −R, y = 0).
At that point: u = U − R²·U·(R²)/R⁴ = U − U = 0 ✓
Verification: far-field recovery
As r → ∞, both correction terms → 0, so u → U and v → V ✓
Far from the obstacle, flow is undisturbed.

Inside the Obstacle

If a particle somehow ends up inside the cylinder (for example, due to a large timestep or a screen-edge wrap that teleports it), its velocity is set to zero and it is immediately relocated to a random valid position outside the obstacle.

4 Turbulence

Plain English: Real flows are never perfectly uniform — individual particles drift slightly faster or slower than the average. The turbulence control adds a small random velocity offset to each particle. The offsets are drawn once at startup (or when the user re-seeds) and stay with each particle for its lifetime.

Per-Particle Velocity Offset

At initialisation, each particle receives a random velocity perturbation:

Eq. 9 θ ~ Uniform[0, 2π] ← random direction speed ~ Uniform[0, T] ← T = turbulence amplitude (px/s) dVx = speed · cos(θ) dVy = speed · sin(θ)

During each frame, the total velocity supplied to the flow field equation is:

Eq. 10 Vx_total = Vx_mean + dVx Vy_total = Vy_mean + dVy

These totals are then passed into the flow field calculation (Eq. 7 when an obstacle is present, Eq. 3 when not). The ground truth readout always shows the mean flow, not per-particle values. The perturbations are re-drawn only when the user presses R (re-seed).

5 Particle Appearance (Gaussian Spot)

Plain English: Real camera sensors see out-of-focus particles as blurry discs, not sharp dots. The tool models this correctly: each particle is drawn as a bright spot that fades smoothly from its centre outward, following a bell-curve (Gaussian) brightness profile.

Gaussian Intensity Profile

For each pixel (px, py) in the particle's sprite, the brightness is:

Eq. 11 r² = (px − cx)² + (py − cy)² ← squared distance from centre I = B · exp(−r² / 2) ← σ = 1 unit in sprite space

B is the brightness setting (0–255). The sprite is pre-computed once and then scaled to the particle's actual radius when drawn on screen, so a particle with radius 3 px uses a 3× scaled version of the same unit sprite.

Particles are composited using additive blending: where two particles overlap, their intensities add together. This is physically correct — more photons arriving at the same sensor pixel produce a brighter reading.

6 Image Noise Models

Plain English: Real cameras add three types of random noise to every image. The tool simulates all three, which is important for testing whether a PIV algorithm still measures the right velocity even when the image is imperfect.
Noise typePhysical originMathematical model
Read noise Electronic noise in the sensor readout circuit; present even in total darkness Gaussian: each pixel gets an offset drawn from N(0, σ) where σ = read noise setting (DN)
Shot noise Quantum nature of light — photon arrival is statistically random (Poisson process) Poisson approximated as Gaussian: σ ≈ √(scale × I) per pixel, where I = brightness
Background pedestal Dark current, stray light, or sensor offset Flat additive constant added to every pixel before noise is applied

Combined Noise Formula

Eq. 12 pixel_value = clip( background + N(0, σ_read) + |N(0, σ_shot)| , 0, 255 ) where: σ_shot = √( shot_scale × B )

The absolute value on the shot noise term prevents negative contributions (shot noise is always positive — you cannot have fewer than zero photons arrive). The clip function keeps the output in the valid 0–255 range.

The noise texture is regenerated approximately every 4 render frames (~15 Hz at 60 fps) using a pre-computed table of Gaussian samples generated by the Box-Muller transform at startup.

7 Timing and Displacement

Plain English: The readout at the bottom of the screen shows how many pixels a particle moves per frame — both at the TV's own refresh rate and at the camera's frame rate. These are different numbers, and understanding the difference is the whole point of the tool.

Per-Frame Displacement

Eq. 13 speed_px_s = √( Vx² + Vy² ) ← magnitude in px/s Δpx_TV_frame = speed_px_s / display_fps ← displacement per TV frame Δpx_cam_frame = speed_px_s / camera_fps ← displacement per camera frame

At 0.08 m/s with default scale (~99.8 px/s), 30 fps camera, 60 Hz display:

Δpx_TV_frame = 99.8 / 60 ≈ 1.66 px per TV frame Δpx_cam_frame = 99.8 / 30 ≈ 3.33 px per camera frame

True Speed (Ground Truth)

The "True Speed" shown in m/s is calculated by inverting the scale:

Eq. 14 true_speed_m_s = speed_px_s / px_per_mm / 1000

This should always equal the Vx setting (when Vy = 0), confirming the round-trip conversion is consistent.

8 Ground Truth Error Metric

Plain English: The researcher types in the velocity they measured from the particle video. The tool compares that to the known correct answer and reports the error. A result within 5% is a pass; 5–15% is a warning; over 15% is a fail.
Eq. 15 error_m_s = measured − true_speed % error = ( error_m_s / true_speed ) × 100
|% error|VerdictMeaning
< 5 %PASSMeasurement is within acceptable PIV accuracy
5 – 15 %WARNMarginal — review image quality, window size, or seeding density
> 15 %FAILSignificant error — likely a calibration or algorithm issue

9 Random Number Generator (Reproducibility)

Plain English: For scientific reproducibility, the tool can generate the same particle layout every time from a given "seed" number. The same seed always produces the same result — so two researchers at two different computers can compare measurements on an identical scene.

The seeded generator uses the Mulberry32 algorithm, a well-known and statistically robust pseudo-random number generator (PRNG) for 32-bit integers:

Eq. 16 state += 0x6D2B79F5 z = state z = (z ⊕ (z >> 15)) × (z | 1) z += (z ⊕ (z >> 7)) × (z | 61) output = (z ⊕ (z >> 14)) / 2³²

Gaussian-distributed noise samples are generated separately using the Box-Muller transform, which converts two uniform random numbers into a pair of normally-distributed samples:

Eq. 17 z₁ = √(−2 ln u₁) · cos(2π u₂) z₂ = √(−2 ln u₁) · sin(2π u₂) where u₁, u₂ ~ Uniform(0,1)

10 Known Limitations (Not Bugs)

The following are deliberate simplifications of real-world physics. They do not affect the validity of the tool for PIV ground-truth testing, but are worth understanding:

No viscosity or boundary layer. Real fluids have friction at the cylinder surface, creating a thin zone of slower-moving fluid (the boundary layer). Potential flow ignores this. In real experiments at typical river flow speeds, a turbulent boundary layer would cause flow separation at roughly 80–90° around the cylinder and a chaotic wake behind it.
No drag force (D'Alembert's Paradox). Potential flow theory predicts zero drag on the cylinder. This is mathematically correct within the assumptions of the model but does not match real fluid behaviour. It does not affect particle trajectories outside the immediate vicinity of the cylinder.
No vortex shedding. At Reynolds numbers above about 40, real flow past a cylinder produces alternating vortices (the von Kármán vortex street). The potential flow model is steady and symmetric — no shedding is present.
2-D only. All flow is computed in the plane of the screen. There is no depth dimension, which is consistent with the intended use case of a 2-D display-based PIV system.

Summary — What Has Been Verified

  • Scale conversion from m/s to px/s is correct (Eq. 1–2)
  • Position update uses standard explicit Euler integration (Eq. 3)
  • Flow field formula around cylinder matches the classical analytic solution for potential flow (Eq. 7)
  • The no-penetration boundary condition at the cylinder surface is algebraically confirmed to be satisfied (Eq. 8)
  • Far-field recovery (undisturbed flow far from cylinder) is confirmed (Section 3)
  • Stagnation point location is confirmed at the upstream face (Section 3)
  • Turbulence is isotropic with uniform random magnitude (Eq. 9–10)
  • Gaussian particle profile uses σ = 1 unit in sprite space, scaled to physical radius (Eq. 11)
  • Noise models correctly represent read noise (Gaussian), shot noise (Poisson/Gaussian approx.), and background pedestal (Eq. 12)
  • Ground truth error metric uses standard percentage error (Eq. 15)
